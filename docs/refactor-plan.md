# Split_kMeans refactor plan (v2.0.0)

Goal: correct, reproducible, fast and maintainable split k-means experiments for the master's thesis, and the final thesis results in the format of the approved seminar presentation.

Rules: refactors keep golden outputs bit-identical. Algorithm changes are one commit each, with `make golden-update`, a changelog entry and before/after statistics. Code comments are unverified claims, not a source: the code defines current behavior, the primary literature or your decision defines intended behavior. Milestones M0 to M4 (below) check real data at fixed points. Thesis times come only from release builds at log level 1 on one reference machine (D3), taken from `<Algo>_runs.csv` (RS: the time of the last SSE improvement of each run, from `_log.csv` through `report`; 3.10).

Commit workflow (from 6.7 onward; you decided 2026-11-23): after completing and verifying each plan step, commit that step with a descriptive message naming the step, including milestone and documentation- or results-only steps. Keep any separately required commits, such as the 6.7 report fix, and do not include unrelated pre-existing changes. Never push unless you explicitly request it.

Build target for the professor: `make && make check` in the repo root (Linux). Visual Studio 2026 project kept in `msvc/`. Supported platforms: Linux and Windows (MinGW-w64, Visual Studio 2026). macOS is not supported (see Open decisions).

Default settings (professor's requirement): the exe runs with no arguments (batch mode) and with `-k K data.txt [gt.txt]`. Every new option defaults to today's behavior; `make check` smoke-tests both invocations.

Thesis results (seminar presentation approved by the thesis supervisor, 18.06.2025; local copies: `university/course/out/md/Seminaari_180625.md`, v1 data in `university/excels/`): SKM-Intra, SKM-Global and SKM-Local against RKM, RS, bisecting k-means and Split-PCA on the local SIPU sets (23 today: the original 19 plus four DIM sets, D6); measures time, SSE, CI and success rate. Deliverables: tables of average CI, success rate and time (algorithms × datasets, slides 53 to 55); per-dataset graphs of SSE and CI against time on a log scale (RS and RKM as curves, the other algorithms as end points; slide 50 and `seminaari_TimeGraphs – KM.xlsx`); MATLAB cluster figures from snapshots (`visuals/generalizedplotting.m`, 3.3b), including a few step-by-step splits (the thesis supervisor's request; slides 29 to 31) and a local repartition figure from our own runs (slide 36 shows Rantinoja 2023 Fig. 4.13, p. 38). RS results (tables and graphs) end at the last SSE improvement of each run (you decided 2026-11-20, replacing the first CI = 0 of 2026-11-19: RS keeps improving its SSE after it reaches CI = 0, as the v1 graphs show; in M1, S4 reaches CI = 0 at swap 50 (16 ms) and improves until swap 4003 (1358 ms) of 5000 (1706 ms)); the program logs the initial solution and every improvement, and only `report` (3.9, 3.10) ends the RS results at the last one, so runs that go through `report` need tracking rows. The v1 graphs that the thesis supervisor accepted used one RS run and one RKM run per dataset, both drawn to the end of the run (all 19 graph sheets; RKM over its 1000 repeats, RS past its first CI = 0, for example S4: CI = 0 at 44 ms, line to 7591 ms); v2 keeps that format, except that the RS curve now ends at its last improvement and RKM still runs to the end. Split-PCA results are copied by hand from CBModules runs (integration: Future work F1).

Milestones (real data, seed 20261119, one release build (MinGW gcc, the expected thesis build until 5.1 confirms it, D3), log level 1, run folders outside OneDrive, summaries in `results/` (D4)). Main group: s1, s4, a3, unbalance, dim064 and worms_2d (worms_2d without SKM-Global, RKM and RS); algorithms km, skm-intra, skm-global, skm-local, bisecting, rkm and rs; development budget (D1): 100 runs on the five small sets, 10 on worms_2d, RKM and RS 1 run; about 3 minutes with the current code (about 10 at v1 speed). Hard group (you decided 2026-11-20): birch1, birch2, birch3 and worms_64d, the sets where the split variants did not reach CI = 0 in v1; skm-intra and skm-local 100 runs, skm-global 10 runs; about 52 minutes (pilot 2026-11-20, one run each: SKM-Global 54 s on birch1, 7 to 17 s on the others; SKM-Intra and SKM-Local 0.2 to 9 s); compare mean CI there (with 10 runs a success rate moves in 10 % steps). The main group runs at every milestone; the hard group only at M0 and M4, because M1 to M3b are exact refactor checks that the main group covers (including the decimal coordinates of worms_2d). Until 3.3 they run in CLI mode, because batch mode writes tracking rows inside the timed code; from 3.10 every milestone call adds `--track-progress --snapshots none` (paused rows cost no measured time; `report` needs them for RS). M1, M2, M3a and M3b must reproduce the SSE and CI of the main group exactly with `compare_runs` (M1 to M3a: M0; M3b: the reference run before 7.1), which also covers the last-bit changes that the integer golden data cannot see; any run count is an exact check. M4 runs before and after each Phase 6 step, main and hard group, with only the algorithms the step changes (for example 6.1: SKM-Local, about 16 minutes on the hard group per run).
